# Session 2026-10-22, Neoverse-N1, 4 cores (replay)

A replay run of the SDK comparison on the same four-core Arm server as `2026-10-22-neoverse-n1-4core`. Instead of answering immediately with a fixed synthetic body, the peer replays the 120 provider responses recorded in `replay/recordings/2026-10-22/` (`claude-sonnet-5-5` on Anthropic Messages and `gpt-6-luna` on OpenAI Chat Completions, 30 buffered and 30 streamed each) at their recorded arrival times. `tables.md` is generated from the records in this directory by `render.py` (`python3 render.py <this directory> > tables.md`), and `tests/test_results.py` fails if the file differs from that output. This page describes the session; it quotes no measured number, so every number is in `tables.md` or in the records.

## What was run

- Same machine and CPU pinning as `2026-10-22-neoverse-n1-4core`: four Neoverse-N1 cores, Ubuntu 24.04, peer and its two serving processes on CPUs 0 and 1, client under test on CPUs 2 and 3.
- `python3 sdkbench.py run --workload workload-replay.json --replay replay/recordings/2026-10-22 --contenders null-curl,sp,ai-sdk-cpp,rust-genai,openai-py,anthropic-py,litellm,any-llm,aisuite,vercel-ai --reps 2 --reruns 1 --peer-cpus 0,1 --peer-workers 2 --client-cpus 2,3 --timeout 600`, from the clean harness commit named in `session.json`.
- Both APIs (OpenAI Chat Completions, Anthropic Messages), both modes (buffered, streamed), concurrency 1, 16 and 128, two fresh client processes per cell, HTTP/1.1, pool size equal to the concurrency where the SDK allows it. Because each replayed response takes between 0.65 s and 4.2 s, `workload-replay.json` runs 24 measured requests at concurrency 1 and 4 per in-flight slot at concurrency 16 and 128 (64 and 512 requests).

## Things to know before reading the tables

- **What replay changes.** In the instant-peer session (`2026-10-22-neoverse-n1-4core`), a 50-chunk SSE stream arrives in one or two socket reads and a request completes in under a millisecond, so throughput and latency are bounded by the loopback peer at concurrency 8 and above. In a replay session, each response arrives over seconds in dozens of separate socket reads (`body pieces p50` in the Recordings table), so the peer is nearly idle (peer lag stays well below the 2,000 µs mark in every cell) and the client wakes up on each arriving piece.
- **Residual latency.** Client p50 latency is dominated by the recorded provider pace (2–3 s). The residual column subtracts the mean time the peer took to send the replies of that window (scheduled duration plus peer timer lag) from the client's mean request latency, leaving what the client and loopback exchange added on top of the provider's schedule (including any client-side connection pool or thread-pool queuing at high concurrency).
- **Connection reuse under real response durations.** Every contender except `vercel-ai` met the zero-new-connections gate on the first attempt in every applicable cell (`2 of 2`). `vercel-ai` passed at concurrency 1 (`2 of 2`) and opened new connections inside the measured window at concurrency 16 and 128 (`0 of 4`), because the spread between the fastest and slowest replayed responses in a wave exceeds the 4-second default idle `keepAliveTimeout` of Node's `fetch` (`undici`) pool. Those attempts are listed under `Invalid attempts` in `tables.md`.
- **Single-thread pool and connection caps at concurrency 16 and 128.** As in the instant-peer session, `aisuite`'s synchronous `anthropic` call runs on `asyncio`'s default thread pool (`min(32, cpu_count + 4) = 8` threads on 4 cores), and the `httpx`-based Python clients (`openai-py`, `anthropic-py`, `litellm`, `any-llm`, `aisuite`) cap their default pool at 100 connections, so at concurrency 128 the extra 28 in-flight calls wait for a pool slot for the full 2–3 s duration of a replayed response.

## Files

| file | content |
|---|---|
| `session.json` | provenance: harness commit and dirty flag, CPU model and count, kernel, tool versions, UTC time, hashes of the scripts, workload, manifest and recordings, and the installed record of every contender |
| `cells.jsonl` | one record per attempt of every cell (including invalid attempts and n/a cells) |
| `samples/` | raw per-request latencies of every cell, gzip-compressed JSON |
| `logs/` | stderr of every client process |
| `runner.log` | the runner's console output |
| `load-after.txt` | load average and top processes immediately after the session |
| `tables.md` | the tables, generated by `render.py` |
