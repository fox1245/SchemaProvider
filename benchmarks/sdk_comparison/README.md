# SDK comparison harness

A reproducible comparison of SchemaProvider with other LLM client SDKs. Every client sends the same requests to the same mock TLS peer; the harness records latency, throughput, client CPU, memory, cold start and install footprint, and `render.py` turns the records into tables. This directory contains no measured numbers: results live in a session directory that `sdkbench.py` writes, and every table is generated from it.

What the comparison measures is the client side of a request to a model-free peer on the same machine: request construction, the HTTP exchange, response or stream decoding, and whatever else the SDK does per request. It says nothing about model latency or network behaviour.

## Layout

| path | content |
|---|---|
| `workload.json` | the one workload: messages, token cap, reply size, chunk count, concurrency levels, sample counts |
| `contenders.json` | the manifest: how each client is started, its connection-reuse expectation, its footprint path, what it does per request |
| `pins.json` | what is installed: commits, release versions, toolchains, dependency resolution date |
| `locks/` | hash-locked requirement files (Python), generated by `scripts/lock.py` |
| `clients/` | one small client program per contender, plus the shared measurement loop of each language |
| `scripts/install.py` | installs the contenders from the pins, with no credentials in the environment; `scripts/clean.py` removes what it created |
| `sdkbench.py` | the runner: starts the peer and one client process per cell, writes records |
| `render.py` | records to Markdown tables |
| `tests/test_peer.py` | checks of the peer's request validation and options |
| `../../tools/benchmark_peer.mjs` | the mock peer (SchemaProvider's independent protocol oracle, with options added for this comparison) |

## Method

**Peer.** One Node TLS server serves the OpenAI Chat Completions and the Anthropic Messages wire formats with fixed, valid replies: a buffered JSON reply, or an SSE stream of 50 text deltas of about 24 bytes each (OpenAI: a role chunk, 50 content chunks, a final chunk with usage, `[DONE]`; Anthropic: the full event sequence). Both replies carry the same text, which every client must reproduce exactly. The peer validates each request and answers 400 to a request that differs from the workload: route, model, token cap, stream flag, credential header, system prompt and user prompt. The runner rejects a cell in which the peer rejected anything. Each cell starts a fresh peer with an ephemeral CA, which the client trusts through its normal mechanism (`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, a reqwest root certificate, a libcurl `CAINFO`); certificate verification is never disabled.

**HTTP/1.1 everywhere.** The peer offers HTTP/1.1 only, and every client is configured for it. HTTP/2 multiplexing on one connection and N HTTP/1.1 connections are different workloads for the peer, and not every client supports HTTP/2.

**Closed loop.** Each client keeps exactly `concurrency` requests in flight and issues the next as one completes. The numbers are service times at fixed concurrency, not response times under an arrival rate.

**Warm connections.** Before a measured window every client runs warm-up rounds at the full concurrency. The peer holds the replies of the first N requests until N are in flight, so N connections exist. The runner then asks for another round until a whole round opened no new connection (at most 8). It reads the peer's connection counter before and after the window and requires **zero new connections inside it**. A client that opens a connection per request (declared `connection_reuse: false` in the manifest) is not held to this and its record says how many connections it opened. A client for which the manifest carries a `pool_note` (an SDK that cannot size its pool, or that drops connections on its own) is flagged instead of rejected, gets at most three warm-up rounds, and its record states how many connections the window opened. A client whose manifest carries a `concurrency_cap_note` (a hidden thread pool that caps the requests actually in flight) runs without the barrier and is flagged. A cell that comes out invalid is run once more (`--reruns`); every attempt stays in the records and the tables use the valid ones.

**Pool parity.** Where an SDK exposes a connection-pool size, it is set to the concurrency (an idle-connection limit of 100 or 4 would otherwise make the larger cells open connections). Each record states what was set, or that the SDK offers no knob.

**Per-request count.** The peer counts the requests of the window. A cell is invalid unless the peer saw exactly the measured number, which exposes silent retries.

**Verification outside the timed region.** The clock of a request stops when the SDK call returns (buffered) or when the stream is fully consumed (streamed). Streamed clients collect the non-empty text deltas of each request into a list or string while consuming the stream (that is part of what an application does with a stream). Text extraction from a buffered response, the comparison with the expected text and the delta count happen after the clock has stopped.

**Percentiles.** Nearest-rank on the samples pooled over the repetitions. p99 is printed only if every repetition has at least 1,000 samples; the measured request count per cell is `max(1000, 20 × concurrency)`. The raw samples of every cell are stored next to the records.

**Memory.** Peak RSS is `VmHWM` of the process at the end of the window and includes the interpreter or runtime and its imports. Marginal memory per in-flight request is the difference between the peak at concurrency N and at the lowest concurrency, divided by the difference in concurrency, from separate fresh processes.

**CPU.** User plus system time of the whole client process over the measured window, from the process's own usage counters (`getrusage`, `process.resourceUsage`), divided by the number of requests.

**Peer cost.** The peer's CPU time during the window and the connections it accepted are recorded. They are never subtracted. A cell during which the peer used at least 80% of the cores it could use (one per serving process, at most one per connection) is marked in the tables: it measures the peer as much as the client.

**Cold start.** Wall time from spawning the process to its first completed, verified request against a running peer, over at least 20 fresh processes (one uncounted spawn first, so that the program's files are in the page cache).

**Null client.** `null-curl` is a small C program that sends the same requests over libcurl's multi interface, one thread, reusing connections, parsing nothing. `null-curl-fresh` is the same program with `--fresh`, which forbids connection reuse: the floor for a client that opens a connection per request. `--default-cache` (an experiment, not a table row) leaves libcurl's connection-cache size at its default instead of setting it to the concurrency.

## Two libcurl builds

Everything in the comparison that links libcurl runs against two builds, each in its own rows: the distribution's libcurl, and the newest release built from the official tarball into a private prefix (`install.py` steps `libcurl`, `sp-curl823`, `null-curl-curl823`; the tarball's sha256 is checked against the published digest). Both use the system OpenSSL, so the TLS library is the same; they differ in the libcurl version, in the nghttp2 version (the private build has its own nghttp2 because the host has no development files for it), and in the optional libraries each was configured with (the private build has no compression, PSL, IDN, LDAP, SSH or RTMP, which neither client uses). The SchemaProvider tree, compiler flags, CA file and options are the same. Rows carry the libcurl version in their label and are never mixed. Clients that do not link libcurl (ai-sdk-cpp, genai and the other languages) have one row.

## Results

Sessions are directories under `results/`, each with its records, raw samples, provenance, a README that describes the session and its caveats, and `tables.md` generated from the records. A session directory is not edited once it is committed. The first one is [2026-10-22-neoverse-n1-4core](results/2026-10-22-neoverse-n1-4core/README.md).

## Fairness rules

- Each SDK is used the way its own documentation recommends for this task, with one client object reused across requests.
- Nothing is tuned for one side only. Settings that are changed from an SDK's default are the pool size, the HTTP version, and the trust store; each is changed the same way for every client that can take it and recorded in the result of every cell.
- A contender that cannot do a cell is n/a with the reason; the tables list them.
- What each SDK does per request that others may not (retries, validation, typed parsing, cost tracking, logging, telemetry) is listed with the tables, and telemetry is disabled where the SDK allows it.
- Installation hygiene: every contender is pinned (commit, or release with the hashes of its files), installed into an environment of its own, from an environment with no credentials in it. The only credential string anywhere is a fixed fake key that the peer checks. Python dependencies are installed with `pip --require-hashes`, JavaScript packages with `npm ci --ignore-scripts` from a lockfile, Rust crates with `cargo build --locked`.
- LiteLLM is a release, not the head of its default branch: an exact version that no published advisory lists as affected, installed from hashes taken from PyPI's JSON API, with a check that no unexpected `.pth` file exists in the environment.

## Running

```sh
# 1. install (needs network; the build parts take a while)
python3 scripts/install.py --install DIR

# 2. measure; pin the peer and the clients to disjoint CPUs on a multi-core host
python3 sdkbench.py all --install DIR --out results/SESSION --reps 5 --peer-cpus 0,1 --peer-workers 2 --client-cpus 2,3

# 3. tables
python3 render.py results/SESSION > tables.md
```

Pins are the head of each default branch on the day they were resolved (see `pins.json`); `scripts/repin.py` moves them to the current heads, and its header lists the commands that regenerate the lock files.

`sdkbench.py run|cold|sizes` run one phase. `--contenders`, `--apis`, `--modes` and `--concurrency` select cells; `--client-args=--name value` appends options to every client's command line, for experiments only (the SchemaProvider and null clients take `--io-threads`, `--workers`, `--max-host-connections` and `--default-cache`; the others reject unknown options); `--requests` and `--warmup` override the counts for a functional smoke run (the tables then print no p99, because the samples are too few).

A session directory holds `session.json` (provenance: harness commit and dirty flag, CPU model and count, governor, kernel, tool versions, UTC time, hashes of the runner, renderer, workload, manifest and peer, and the installed record of every contender), `cells.jsonl`, `cold.jsonl`, `sizes.jsonl`, `samples/` (raw per-request latencies) and `logs/` (client stderr). Treat a session directory as immutable once it has been rendered.

## Client line protocol

A client is started with the workload on its command line (`--api openai|anthropic --mode buffered|stream --concurrency N --warmup W --requests M --base-prefix URL --ca FILE --model --system --user --max-tokens --expect --chunks --api-key`, and `--cold`). It prints JSON lines on stdout:

1. After each warm-up round of `W` requests: `{"event":"ready"}`, then reads a line: `MORE` runs another round, `GO` starts the measured window.
2. After the window: one `{"event":"result", ...}` line with `ok`, `failed`, `first_error`, `verify_failed`, `wall_ns`, `cpu_user_us`, `cpu_sys_us`, `rss_ready_kb`, `hwm_ready_kb`, `rss_end_kb`, `hwm_end_kb`, the `config` it used and the raw `latency_ns` array.
3. With `--cold`: one request, then `{"event":"first","ok":true|false}`.

## Known limits

- The peer is Node, one process unless `--peer-workers` says otherwise. At high request rates it, not the client, is the bottleneck; the tables mark such cells and record the peer's CPU.
- Everything runs over loopback on one host, so network and kernel effects are small and the same for every client.
- The workload has no tools, no images and no reasoning content.
